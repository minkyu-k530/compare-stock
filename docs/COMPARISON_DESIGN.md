# 비교 지표와 연구 설계

> 확인일: 2026-10-27. 상태: **공개 자료 조사와 설계 정리 완료, 이 문서의 새 지표(①②④⑤)는 실측 0건.** 토스 SLASH 23·24는 세션 소개 페이지만 확인했고 발표 슬라이드 본문은 읽지 않았다. 장애 보도는 기사 요약 기준이며 발생 연도는 원문으로 다시 확인해야 한다.

## 1. 질문을 바꾸는 이유

같은 탭에서 "몇 ms 걸렸나"를 재고 그 원인을 따지는 비교는 외부에서 원인을 가를 수 없다. 화면 시간에는 사용자 망, 회사별 서버 경로, 서버 처리, 캐시, 렌더링, 측정 시각의 시장 상황이 함께 들어 있다. 그래서 질문을 세 가지로 나눈다.

1. **망의 영향이 짝으로 상쇄되는 지표**로 두 앱을 비교한다.
2. **망을 원인이 아니라 실험 조건(자극)으로 쓴다.** 일부러 끊거나 느리게 만들고 반응을 본다.
3. **원인 검증은 직접 통제하는 시스템**에서 한다. 외부 앱 관찰과 섞지 않는다.

같은 Wi-Fi에서 잰 "탭 → 가격 표시" 시간은 버리지 않는다. [본 실험 계획](EXPERIMENT_PLAN.md)대로 측정하되 **원인 설명 없이 기술 지표로만** 보고한다.

## 2. 공개 자료 조사

| 항목 | 토스증권 | 한국투자증권 |
|---|---|---|
| 시세 경로 | SLASH 22(2022): 원장(유닉스·C) → Kafka → WebSocket 서버 → 클라이언트. 차트·호가·현재가는 WebSocket, 실패하거나 늦으면 폴링 API로 대체. 시세 서버는 IDC에서 운영, AWS 이중화 POC 완료 | 이번 조사 범위에서 모바일 앱 시세 경로를 설명한 공개 기술 발표를 찾지 못함 |
| 이후 공개된 주제 | SLASH 23: 시세 플랫폼 구조와 개발 과정. SLASH 24: SSE 푸시로 불필요한 폴링 제거 | 개발자용 Open API: REST와 WebSocket 실시간 시세(체결가, 호가) |
| 공개된 설계 디테일 | AWS 기술 블로그(2025-04-22): 미국 옵션 원천 시세를 us-east-1의 Amazon MSK·EKS에서 받아 서울로 전송. 옵션 계약별 초당 3건으로 갱신 제한(슬라이딩 윈도). 호가는 Kafka `ack=0`, 체결은 `ack=all`. 개장 시 초당 200만~300만 이벤트 | REST에 초당 호출 한도가 있다(제3자 자료 기준 실전 초당 20건). 공식 수치는 KIS Developers 포털에서 확인해야 함 |
| 장애 보도 | MTS만 약 8분 접속 불가, WTS는 정상이었다는 보도. 금감원 보고 기준 해당 연도 4건이라는 보도(연도 원문 확인 필요) | 장 초반 MTS 접속 지연·호가 조회 오류, 2022년 8월 약 15시간 만에 복구된 HTS·MTS 장애 보도. 업계 MTS·HTS 장애는 2020년 60건에서 2024년 94건(국회 자료 인용 보도) |

**결론: 공개 자료가 비대칭이다.** 토스는 설계 일부가 공개되어 있고, 한국투자증권은 모바일 앱 내부 구조에 대한 공개 자료를 이번 조사에서 찾지 못했다. 따라서 "한국투자증권의 구조 때문에 이런 결과가 나왔다"는 결론은 근거를 만들 수 없다. 자료가 적다는 사실을 구조가 단순하거나 나쁘다는 뜻으로 읽지도 않는다. 할 수 있는 말은 두 가지다.

- 토스의 공개 설계가 관찰 가능한 지표에서 예측대로 드러나는가.
- 두 앱의 관찰 가능한 행동이 어떻게 다른가.

Open API는 외부 개발자용 제품이다. 한국투자 모바일 앱이 같은 경로를 쓴다는 근거로 쓰지 않는다. 토스의 2022~2025년 자료도 현재 앱의 모든 화면이 같은 방식이라는 근거가 아니다.

## 3. 비교 지표

| 지표 | 망 문제를 어떻게 피하나 | 측정 | 공개 설계와 연결 |
|---|---|---|---|
| **① 시세 신선도·갱신 빈도** | 같은 거래소 체결이 같은 순간 두 앱에 도착한다. 한 화면에 두 앱을 같이 녹화하면 시간대·장 상황·사용자 Wi-Fi를 두 앱이 공유해 사건마다 짝이 된다 | 분할 화면 녹화로 같은 가격 변화가 각 앱에 뜬 시각의 차이, 초당 화면 갱신 횟수 | WebSocket 푸시, 종목별 갱신 제한 같은 설계가 화면의 갱신 간격으로 드러나는지 |
| **② 망 끊김 후 회복** | 망 상태가 원인이 아니라 실험 조건이다. 한 번 끊으면 두 앱이 같은 끊김을 겪는다 | 끊김 해제 후 시세가 다시 움직이기까지의 시간, 끊긴 동안 오래된 값을 그대로 보이는지 | 토스는 "WebSocket 실패 시 폴링으로 대체"를 공개했다 |
| **③ RTT 민감도** | 망을 자극으로 쓴다 | [RTT 단계별 실험](ARCHITECTURE_INFERENCE.md)의 기울기 k | 탭 뒤 망을 얼마나 기다리는 화면인지에 대한 후보 |
| **④ 클라이언트 지표** | 망과 거의 무관하다 | 콜드 스타트 첫 화면까지 시간, 스크롤·차트의 프레임 끊김 | 렌더링·앱 구조 |
| **⑤ 표시 정확성** | 망과 무관한 화면 품질이다 | 화면 전환 중 0, 빈칸, 이전 종목 가격이 보이는 프레임 수 | 화면 상태 초기화·재사용 방식 |

### ① 시세 신선도·갱신 빈도 (우선 추천)

장중 10분만 녹화해도 수백 건의 가격 변화가 나온다. 표본을 빨리 모을 수 있고, 시세 플랫폼이 실제로 다루는 지표다.

**사전 확인 (5분):**

1. Galaxy 분할 화면에 두 앱의 같은 종목 상세를 나란히 띄운다. Android 10 이상은 분할 화면에 보이는 앱이 모두 실행(RESUMED) 상태를 유지한다.
2. 장중에 두 앱의 가격이 모두 계속 바뀌는지 본다. 한 앱이 분할 화면을 거부하거나 갱신을 멈추면, 휴대폰 두 대를 나란히 놓고 외부 카메라로 함께 찍는 방식으로 바꾼다.
3. 두 앱이 **같은 시장 기준 가격**(KRX, NXT, 통합 등)을 보이는지 확인한다. 기준이 다르면 같은 사건이 아니므로 비교하지 않는다.

**측정:**

- 같은 종목을 고정하고 화면 녹화 60fps로 10분 녹화한다. 거래가 활발한 종목과 시간대를 고르고 세션 메모에 남긴다.
- 프레임 PTS로 각 앱의 가격 숫자가 바뀐 시각을 판독한다. 처음에는 30~50건을 손으로 판독하고, 필요하면 자동 판독 도구를 만든다.
- **사건 짝:** 두 앱에서 같은 가격 전환(예: 71,200 → 71,300)을 찾아 `토스 표시 시각 − 한투 표시 시각`을 구한다. 한쪽에만 나타난 전환은 따로 센다.
- **갱신 빈도:** 앱별 초당 화면 가격 변경 횟수와 변경 간격 분포를 구한다.

**해석의 한계:**

- 남는 차이는 각 회사의 시세 경로 전체(서버, 서버에서 휴대폰까지의 망 경로, 앱)다. 어느 구간 때문인지는 이 지표만으로 모른다.
- 가격이 같으면 이벤트가 와도 화면은 바뀌지 않는다. **화면 갱신 간격은 전송 주기가 아니다.**
- 나중에 KIS Open API 실시간 체결 스트림을 기준 시계로 추가할 수 있다. 본인 계정과 약관 범위에서만 쓴다. 그 스트림도 한 회사의 한 경로이므로 거래소 시각의 대용으로 단정하지 않는다.

### ② 망 끊김 후 회복

1. ①과 같은 분할 화면에서 녹화를 시작한다.
2. 비행기 모드를 켜고 5초 뒤 끈다. 장중 활발한 종목에서 같은 절차를 5회 반복한다.
3. 앱별로 기록한다: 끊긴 동안의 표시(오래된 값, 경고, 빈칸), 끊김 해제부터 가격이 다시 바뀐 첫 프레임까지의 시간, 연결 상태 표시 유무.

Wi-Fi 재연결 시간은 두 앱에 같다. 그래도 "다시 바뀐 첫 프레임"은 시장 거래에 따라 늦어질 수 있으므로 같은 사건 짝(①)으로 함께 읽는다.

### ③ RTT 민감도

[RTT 단계별 실험](ARCHITECTURE_INFERENCE.md)을 따른다. 기울기 k는 **이 구성에서 관찰한 RTT 민감도**다. 정확한 왕복 수, API 수, 서버 내부 구조를 식별하지 않는다. 지연 주입은 실제 핫스팟 보정을 통과한 뒤에만 쓴다.

### ④ 클라이언트 지표

- **콜드 스타트 첫 화면(TTID):** `adb shell am force-stop <패키지>` 뒤 `adb shell am start -S -W <패키지>/<활동>`으로 실행하고, logcat의 `Displayed` 줄을 함께 기록한다. 시스템이 모든 앱에 대해 자동으로 남기는 값이다. 첫 화면까지만 재므로 비동기로 불러오는 데이터는 들어가지 않는다.
- 패키지와 실행 활동 이름은 `adb shell pm list packages`와 `adb shell cmd package resolve-activity --brief <패키지>`로 찾는다.
- **프레임 끊김:** `adb shell dumpsys gfxinfo <패키지> reset` 뒤 같은 스크롤·차트 동작을 하고 `dumpsys gfxinfo <패키지>`의 끊긴 프레임 비율을 비교한다. 플랫폼 버전에 따라 집계 방식이 달라 Perfetto 추적과 숫자가 다를 수 있다.

### ⑤ 표시 정확성

기존 화면 녹화에서 바로 셀 수 있다. 예비 판독에서 한국투자 앱이 다른 종목으로 바꾼 뒤 이전 종목 가격을 잠시 남긴 사례가 이미 있다. 같은 완료 기준으로 "잘못된 값이 보인 프레임 수와 시간"을 앱별로 기록한다.

## 4. 설계 원칙과 레퍼런스

| 원칙 | 이 프로젝트에 적용 | 레퍼런스 |
|---|---|---|
| 측정 편향과 무작위화 | 앱 순서 교차, 라운드별 무작위 순서, 설정 변경 기록 | Mytkowicz et al., ASPLOS 2009 |
| 평균 대신 분포와 꼬리 | 중앙값과 p95/p99, 단계별 분포를 보고 | Dean & Barroso, CACM 2013 |
| 부하 측정의 함정 | 직접 만드는 서버의 부하 테스트에서 요청 간격을 고정하고 coordinated omission을 보정 | Gil Tene, *How NOT to Measure Latency* |
| 체감 기준 | 0.1초·1초·10초 기준으로 차이의 실질적 의미 판단. 예비 측정의 37ms 차이는 0.1초 아래다 | Nielsen의 응답 시간 한계 |
| Android 측정 정의 | 콜드·웜·핫 시작, TTID와 TTFD, 분할 화면 실행 상태 | Android 공식 문서 |

두 앱을 자동 조작하지 않는다. 복호화하거나 인증서 고정을 우회하지 않는다. 회사 서버에 부하를 주지 않는다.

## 5. 결과의 3층 구조

1. **관찰층 (두 앱 비교):** ①~⑤ 지표와 그 한계.
2. **연결층 (공개 설계와 관찰의 대조):** 토스의 공개 설계(WebSocket과 폴링 대체, 갱신 제한, SSE)가 관찰 지표에서 예측대로 나타나는지 확인한다. 한국투자증권은 관찰된 행동과 Open API 문서까지만 말한다.
3. **인과층 (직접 통제하는 시스템):** 공개된 선택지를 하나씩 바꿔 측정하는 모의 시세 서버. 예를 들어 폴링과 SSE/WebSocket, 종목별 갱신 제한, Kafka `ack=0`과 `ack=all`, 재연결과 폴링 대체를 비교한다. 지연(p50/p99), 시세 신선도, 메시지 유실, 서버 CPU를 지연·손실을 넣은 망에서 본다. 이 층의 결과는 **자체 시스템의 인과**이며 두 회사 내부로 일반화하지 않는다.

이 구조에서는 "망은 고칠 수 없다"가 "망이 나빠져도 덜 아프게 설계할 수 있고, 그 효과를 측정했다"로 바뀐다.

## 6. 준비 순서

| 단계 | 할 일 | 완료 기준 |
|---|---|---|
| 1. 자료와 사전 확인 | SLASH 23·24 발표자료를 내려받아 시세 플랫폼과 SSE 구조를 읽는다. 분할 화면 가능 여부와 시장 기준을 확인한다 | 공개 설계에서 나온 예측 목록, 분할 화면 가능 여부 |
| 2. 예비 관측 | 장중 ① 10분 녹화 1회, 가격 전환 30~50건 손 판독. ② 5회. ⑤는 기존 영상으로 | 판독 기준 고정, 지표별 분포 초안. 소수 관측은 경향으로만 기록 |
| 3. 본 관측 | 판독 기준을 고정한 뒤 세션을 반복한다. ③은 핫스팟 보정이 통과할 때만 | 사전에 정한 횟수, 실패·제외 건수 포함 |
| 4. 인과 실험 | 모의 시세 서버 최소판: 폴링과 SSE/WebSocket, 종목별 갱신 제한, 지연 분포 측정 | 한 번에 한 변수만 바꾼 비교표 |
| 5. 정리 | "외부 비교에서 원인을 가를 수 없다는 점을 확인했다 → 사건 짝 설계와 망 자극 실험으로 바꿨다 → 원인은 직접 만든 시스템에서 검증했다"를 한 장으로 정리 | 공개 사실, 관측, 가설, 설계 판단이 구분된 요약 |

## 7. 쓰지 않는 말과 기존 도구의 재사용

- 쓰지 않는 말: "한국투자증권의 구조 때문에", "토스 서버가 빨라서", "HTTP/3 덕분에", "k가 왕복 횟수다".
- 영상 PTS 판독(`tools/measure_video_pts.py`)은 ①⑤에 그대로 쓴다.
- RTT 도구(`tools/hotspot_delay.py`, `tools/make_rtt_ledger.py`, `tools/fit_rtt_slope.py`)는 ③에 쓴다.
- PCAP 분석(`tools/analyze_pcap.py`)은 연결층의 보조 증거로 쓴다. 암호화된 데이터 묶음은 특정 API나 서버 처리시간을 식별하지 못한다.
