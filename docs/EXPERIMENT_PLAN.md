# 첫 실측 실험 계획: 종목 상세 화면의 가시적 완료 시간

이 문서는 **토스 앱 증권 화면과 한국투자 앱의 사용자에게 보이는 지연**을 비교하기 위한 본 실험 계획이다. 앱 내부 서버 시간, 현재 사용 중인 프로토콜, 시세의 최신성은 이 실험으로 판정하지 않는다. 2026-10-15 예비 영상 4건은 서로 다른 조건에 각 1페어씩이며, 본 실험은 아직 시작하지 않았다. 따라서 어느 앱이 일반적으로 빠르다고 쓰지 않는다. 입력 도구와 필드 정의는 [README](../README.md), 촬영·프레임 판독 절차는 [MEASUREMENT](MEASUREMENT.md)를 따른다.

**본 실험 전 계획 수정 기록 (2026-10-15):** 예비 판독에서 상세 화면에 `0`이 먼저 보이고, 다른 종목을 연 뒤에는 이전 종목 가격이 잠시 남는 사례를 확인했다. 따라서 완료 기준을 **선택한 종목의 이름과 그 종목의 0·빈칸·이전 종목 잔상이 아닌 가격 숫자가 함께 읽히는 첫 프레임**으로 명확히 했다. 예비 네 건에는 이 동일 기준을 적용했다. 또한 예비 페어 사이에 종목과 키보드 상태가 달라, `stock_code`와 `keyboard_state`를 구조화해 그룹을 분리했다. 이 수정은 60회 본 실험 전에 이루어졌으며, 예비값은 본 실험 결과에 합산하지 않는다.

## 1. 사전에 고정할 질문과 조건

**질문:** 같은 Android 기기에서 두 앱의 **종목 검색 결과**에 있는 같은 국내 주식 종목을 탭한 순간부터, **상세 화면에서 선택 종목명과 그 종목의 0·빈칸·이전 종목 잔상이 아닌 가격 숫자가 모두 읽히는 첫 순간**까지 몇 ms가 걸리는가?

| 항목 | 첫 실험에서 고정할 값 |
|---|---|
| `scenario` | `search_result_to_detail_quote` |
| `completion_criterion` | `선택 종목명과 0·빈칸·이전 종목 잔상이 아닌 가격 숫자가 함께 읽힘` — 두 앱에 같은 문구 입력 |
| 시작점 | 외부 촬영: 손가락이 화면에 처음 닿는 프레임. 화면 녹화: 탭 표시가 처음 보이는 프레임 |
| 종목·경로 | 두 앱에서 같은 종목을 검색한 **결과 화면**을 준비하고 같은 종목 결과를 탭. 검색어 입력 시간은 포함하지 않음. 검색어·결과 행 위치·키보드 표시 여부를 세션에서 고정 |
| `stock_code`, `keyboard_state` | 본 세션 내내 선택 종목의 6자리 코드 1개와 탭 직전 키보드 표시 상태 1개로 고정. 다른 값은 분석에서 별도 조건 |
| `start_state` | `warm`: 두 앱 모두 로그인 완료, 실행 중이며 해당 검색 결과가 보이는 상태. 측정 전 각 앱에서 해당 종목을 한 번 열고 결과로 돌아오는 준비 동작을 동일하게 수행 |
| `market_phase` | `open`: 측정 당시 정규장 진행 여부를 확인하고 장중 세션만 첫 분석에 사용. 장외 측정은 별도 그룹 |
| 기기·망 | Android 기기 한 대, 같은 Wi-Fi, VPN·셀룰러 자동 전환 없음. 절전 모드와 화면 주사율 설정을 고정 |
| 계정·앱 | 두 앱의 버전, 로그인 상태, 추가 인증 여부를 기록. 앱 업데이트가 일어나면 새 세션으로 분리 |
| 촬영 | 가능하면 외부 120/240fps 촬영. 한 대만 있으면 탭 표시를 켠 화면 녹화. **서로 다른 촬영·판독 방식은 합산하지 않음** |

이것은 **반복 방문의 웜 상태** 실험이다. 준비 동작은 앱 내부 캐시를 동일하게 만든다는 뜻이 아니다. 종목의 실제 가격이 두 화면에서 같은지, 어느 쪽이 더 최신인지는 완료 조건에 넣지 않는다. 종목명·검색 결과 위치, 기기/OS·앱 버전, 실제 화면 주사율, 네트워크 종류, 측정 날짜와 시간대를 세션 메모에 남긴다. 개인정보가 보이는 화면은 촬영하거나 공개하지 않는다.

## 2. 실행 순서와 짝 만들기

측정 전에 **15개 블록 × 4회 = 60회 시도, 30개 계획된 페어**를 확정한다. A=토스, B=한국투자 앱으로 두고 홀수 블록은 `A-B-B-A`, 짝수 블록은 `B-A-A-B`로 실행한다. 한 블록의 인접한 1·2회와 3·4회가 각각 한 페어다. 서로 다른 블록/페어의 `run_id`는 다시 쓰지 않는다.

| 블록 | 1회 | 2회 | 3회 | 4회 | `run_id` 예시 |
|---|---|---|---|---|---|
| 홀수 `A-B-B-A` | 토스, 순서 1 | 한투, 순서 2 | 한투, 순서 3 | 토스, 순서 4 | 1·2회 `20261015-wifi-01a`, 3·4회 `20261015-wifi-01b` |
| 짝수 `B-A-A-B` | 한투, 순서 1 | 토스, 순서 2 | 토스, 순서 3 | 한투, 순서 4 | `…-02a`, `…-02b` |

각 시도 직전에 해당 앱의 같은 검색 결과 화면으로 돌아와 **화면이 안정된 뒤 3초** 기다리고 탭한다. 준비 중 다른 종목을 열거나 앱 데이터/캐시를 지우지 않는다. 시도 사이에는 동일한 준비 절차를 반복한다. 보안 인증 요구, 앱 강제 종료, 통화/알림 가림, Wi-Fi 전환, 발열·절전 상태 변화가 생기면 이유와 해당 시도를 기록하고 그 블록을 정상 블록으로 취급하지 않는다. 네트워크 품질을 숫자 하나로 같다고 가정하지 말고 세션 시간대와 조건 변화를 메모한다.

각 앱 시도마다 `run_order`는 블록 안의 실제 위치 1~4로 입력한다. 가격 표시가 10초 안에 완료되지 않으면 `status=timeout`, `timing_basis=manual`, `elapsed_ms=10000`으로 기록한다. 앱 오류·재로그인 요구는 `status=error`와 관찰 종료까지의 시간, 원인을 `notes`에 기록한다. **느린 시도를 다시 재서 교체하지 않는다.** 앱 오류와 촬영 실패는 구분한다. 촬영 실패/탭 프레임 미확인은 앱의 `error`로 입력하지 않고 별도 시도 대장에 `invalid_capture`로 남기며, 공개 결과에 그 건수와 이유를 적는다. 현재 도구에는 `invalid_capture` 상태가 없으므로 이 대장을 따로 유지해야 한다.

시도 대장에는 최소한 `block, position, run_id, app, actual_local_time, video_file, video_sha256, outcome, reason`을 기록한다. 녹화 실패도 계획된 60회 시도의 분모에서 없애지 않는다.

저장소의 `tools/make_trial_ledger.py`로 60행 대장을 먼저 생성한다. 이 대장의 `actual_local_time`은 현지 시각, `outcome`은 `completed`/`timeout`/`error`/`invalid_capture` 중 하나를 실제 시도 후 입력한다. 시작하지 못한 행은 `not_started`와 이유를 남긴다. `run_id`와 `position`은 앱 입력 폼에 그대로 사용한다. 명령 예시는 [README](../README.md)에 있다.

## 3. 영상 증거와 시간 계산

1. 각 원본 영상에 블록·시도 ID를 붙이고 로컬에서 보관한다. 파일명, 촬영 방식, 원본 파일의 SHA-256, 시작·끝 프레임 또는 PTS, 판독 이유를 측정 대장에 남긴다. 영상 원본은 이 서버에 업로드되지 않는다.
2. **고정 FPS가 확인된 경우에만** `(끝 프레임 − 시작 프레임) / 실제 FPS × 1000`을 사용한다. 가변 FPS 또는 FPS 확신이 없으면 프레임별 표시 시각(PTS)의 차이를 쓴다. 브라우저 재생 위치로 찍은 값은 `playback_seek` 근사치로 저장하고 정밀 프레임 값과 섞지 않는다.
3. 두 경계의 바로 전 프레임을 함께 확인한다. 콘텐츠 완료 프레임은 **선택 종목명과 그 종목의 가격 숫자가 동시에 읽히는 최초 프레임**으로 고정한다. `0`, 빈칸, 이전 종목 가격의 잔상은 완료로 세지 않는다. 이것은 가격의 **최신성 검증**과 다르다. 한 번 정한 판독 기준을 앱별로 바꾸지 않는다. 전체 영상의 일부와 극단값은 재판독하고 변경 전후 이유를 기록한다.
4. 영상 프레임 간격은 60fps에서 약 16.7ms, 120fps에서 약 8.3ms다. 시작·끝 사건은 관측 프레임 사이에서 생길 수 있으므로 두 경계에 각각 약 한 프레임의 판독 한계가 있다. **탭 표시의 실제 접촉 대비 지연, 화면 녹화 부하, 카메라 노출/화면 주사** 같은 체계적 오차는 이 숫자로 해결되지 않는다. 따라서 촬영 방식과 시간 판독 방식을 결과 옆에 표시한다.

화면 녹화 값은 **`탭 표시→콘텐츠`**, 외부 촬영 값은 **`손가락 접촉→콘텐츠`**로 명명한다. 첫 시각적 반응은 `first_response_ms`로 별도 기록하되, 없다고 해서 전체 시간을 추정해 채우지 않는다. 시세가 나타난 첫 프레임은 **새 시세가 서버에서 도착한 시각의 증거가 아니다.**

## 4. 분석·중단·보고 규칙

- 15블록을 마치면 결과가 예상과 다르더라도 중단한다. 중간 결과를 보고 시도를 더하거나 종목·완료 기준을 바꾸지 않는다. 새 세션이 필요하면 변경 조건과 시작 전 계획을 별도로 남긴다.
- 완료된 토스·한투 기록이 한 `run_id`에 하나씩 있고 기기·망·시나리오·촬영/판독 방식·웜/콜드·장중/장외·완료 기준이 맞는 페어만 시간 통계에 포함한다. 두 앱이 모두 완료한 페어가 20개 미만이면 첫 세션을 **예비 결과**로 표시한다.
- 계획 30페어, 실제 시작 시도, 완료/시간 초과/앱 오류/촬영 실패, 유효 페어, 제외 사유를 모두 공개한다. 시간 초과를 10초짜리 완료 시간으로 넣지 않는다. 앱별 완료율과 실패율을 시간 통계 옆에 둔다.
- 기본 결과는 페어별 `토스 − 한투` 시간 차이의 중앙값과 각 앱 중앙값이다. p95와 탐색적 부트스트랩 95% 구간은 도구가 제공하는 조건에서 함께 보고, 페어별 산점도·실행 순서·블록 번호에 따른 추세를 살핀다. 부트스트랩 구간이 0을 벗어나도 **이 기기·이 세션의 관찰 차이**일 뿐 원인 입증은 아니다.
- 원자료 CSV, 익명화한 실험 조건, 프레임/PTS 판독 규칙, 제외 대장을 함께 보관한다. 공개 자료에서 계좌·잔고·알림·인증 정보와 원본 영상의 개인정보를 제거한다. 가상 예시와 실측은 항상 분리한다.

## 5. 결과를 읽기 위한 가설 표

| 관측 | 다음에 확인할 가설 | 이 관측만으로 확정할 수 없는 것 |
|---|---|---|
| 첫 반응만 빠르고 이름·가격 완료는 비슷함 | 애니메이션·스켈레톤·단계적 렌더링 | 서버 응답이 빠르다는 결론 |
| 완료 시간 차이와 화면 끊김이 함께 나타남 | UI 스레드·렌더링·기기 부하 | 네트워크가 원인이 아니라는 결론 |
| 첫 방문과 반복 방문의 차이가 큼 | 캐시·사전 로딩·연결 재사용 | 어느 한 캐시 계층의 적중 여부 |
| 장중/장외, Wi-Fi/셀룰러에서 차이 방향이 바뀜 | 데이터 갱신 빈도·망 지연 민감도·서버 경로 | 특정 전송 프로토콜의 우위 |
| 완료 시간은 짧지만 오류·시간 초과가 더 많음 | 부분 표시·오류 처리·신뢰성의 교환 관계 | 평균 지연만으로 더 좋은 경험이라는 결론 |

웜/콜드, 장중/장외, Wi-Fi/셀룰러, 첫 방문/반복 방문은 **후속 별도 세션**으로 추가한다. 콜드 시작은 앱 실행부터 화면 완료까지의 새 시나리오로 정의해야 하며 이 검색 결과 탭 실험에 섞지 않는다. Perfetto/시스템 추적은 프레임 지연 가설을 점검하는 보조 실험으로 따로 수행한다. 측정 부하가 달라질 수 있어 기본 영상 시도와 합산하지 않는다.

## 6. 프로토콜·원인 주장의 증거 단계

| 단계 | 할 수 있는 말 | 넘지 말아야 할 주장 |
|---|---|---|
| 화면 영상 | 어느 앱의 정의된 화면 완료가 이 표본에서 몇 ms였는지 | 서버 시간, 최신 시세 도착 시각 |
| 시스템 추적·[비복호화 패킷 메타데이터](NETWORK_METADATA.md) | 프레임 지연, TCP/UDP/QUIC로 보이는 흐름, 탭당 신규 연결·재사용 등 **관측 사실** | 특정 화면 API의 HTTP 버전·서버 캐시 적중·인과 |
| 공개 기술 발표/개발자 API 문서 | 발표 시점의 설계나 공개 API에서 지원한 방식 | 현재 소비자 앱의 전송 방식 |
| 해당 앱의 권한 있는 계측 또는 제공자 로그 | 요청별 실제 전송·서버 처리·캐시 여부를 확인할 가능성 | 같은 조건의 대조 없이 특정 요소가 속도를 만들었다는 인과 |
| 자체 모의 시세 서버의 통제 실험 | 동일 클라이언트·데이터에서 전송/캐시/팬아웃을 하나씩 바꾼 영향 | 그 효과가 두 상용 앱 내부에서 그대로 발생했다는 주장 |

이번 프로젝트의 정직한 결론 형식은 **“어떤 조건에서 화면 완료 시간 차이를 관찰했고, 어떤 추가 계측으로 가설을 검증할지”**다. `protocol_observation`에는 확인한 사실과 출처만 적는다. 현재 상용 앱의 비공개 구현을 추정해 “토스가 HTTP/3/WebSocket이라서 빠르다” 같은 문장으로 확정하지 않는다.
