# 아키텍처 추론의 보조 실험: RTT 단계별 화면 시간

> 상태: 2026-10-27 기준 **도구 구현 완료, 실측 0건.** `tools/hotspot_delay.py`는 명령 생성과 dry-run만 단위 테스트했다. 실제 Mac 인터넷 공유에서 지연이 휴대폰까지 걸리는지는 아직 확인하지 않았다. 첫 세션 전에 [4.3 보정](#43-보정-세션-전-필수)을 통과해야 한다. 기울기 분석과 PCAP 직렬 왕복 깊이는 합성 데이터 테스트로만 검증했다.

전체 연구는 [두 회사 아키텍처 추론 로드맵](CASE_STUDY_ROADMAP.md)을 따른다. 이 실험은 화면의 **RTT 민감도**를 측정하는 한 단계이며, 서버 내부 구조를 식별하는 검사는 아니다.

## 1. 이 실험이 답하는 질문

"네트워크는 우리가 고칠 수 없고 상황에 따라 다르다"는 결론에는 두 가지가 섞여 있다.

| 구분 | 예 | 누가 정하나 |
|---|---|---|
| **망 상태** | RTT, 손실, 대역폭 | 외부 변수. 앱이 바꿀 수 없다 |
| **망을 쓰는 방식** | 탭 뒤 직렬 왕복 수, 새 연결 여부, 미리 받기, 캐시, 응답 크기 | 아키텍처가 정한다 |

망 상태를 **실험에서 일부러 바꿀 수는 있다.** 같은 탭을 지연 0·100·200·300ms에서 반복하면 이 조건에서 화면의 지연 민감도를 비교할 수 있다. 같은 민감도를 만드는 구조는 여러 개일 수 있다.

다른 문서와의 관계는 다음과 같다.

| 문서 | 질문 |
|---|---|
| [EXPERIMENT_PLAN](EXPERIMENT_PLAN.md) | 같은 망에서 화면이 몇 ms 걸리나 |
| [NETWORK_METADATA](NETWORK_METADATA.md) | 같은 탭에서 앱이 망으로 무엇을 했나 |
| 이 문서 | 망이 느려지면 화면이 얼마나 더 느려지나, 그것이 패킷 관찰과 맞나 |

## 2. 모델

```
T_화면(Δ) ≈ a + k × Δ
```

- `Δ`: 설정한 추가 지연. 분석기 x축도 이 **설정값**이며, 휴대폰 ping 보정이 통과해야 실제 추가 RTT에 가까운 값으로 해석할 수 있다.
- `k`: 설정 지연 1ms당 화면 완료 시간이 몇 ms 달라지는지 나타내는 **RTT 민감도**. 정확한 API 수·왕복 수·서버 내부 hop 수가 아니다.
- `a`: 추가 지연이 0인 이 세션 기본 경로의 적합값. 네트워크·서버·클라이언트 처리가 포함되어 있다.
- 중첩·여러 endpoint·캐시·전송 적응 때문에 이 값으로 화면 시간을 성분별로 나눌 수 없다.

요청 경로가 고정되고 모든 직렬 왕복에 같은 추가 RTT가 적용되는 **이상적인 가산 모형**에서는 아래 비유를 쓸 수 있다. 이 표는 관측된 k에서 구조를 역으로 확정하는 판별표가 아니다. 새 연결은 재개·0-RTT·Retry 등이 없다는 추가 가정을 둔다.

| 탭 뒤 화면이 기다리는 것 | 예상 k |
|---|---:|
| 로컬 캐시나 미리 받은 데이터로 완료 | ≈ 0 |
| 열려 있는 연결로 API 1회 | 1 |
| QUIC 새 연결 + API 1회 | 2 |
| TCP + TLS 1.3 새 연결 + API 1회 | 3 |
| DNS + TCP + TLS 1.3 + API 1회 | 4 |
| 열린 연결에서 API 2개를 순서대로 | 2 |

병렬 작업은 가장 늦게 끝나는 경로가 화면 완료를 결정할 수 있다. 응답 크기·혼잡 제어·손실·재시도·연결 재개도 민감도를 바꾼다. QUIC에도 full handshake와 0-RTT 등 다른 조건이 있으므로 단일 숫자로 프로토콜을 식별하지 않는다. 근거: [RFC 9001 §4.1](https://www.rfc-editor.org/rfc/rfc9001.html#section-4.1).

## 3. 가설과 예측 (측정 전에 적는다)

각 가설의 예상 양상을 적되 여러 가설이 같은 양상을 만들 수 있음을 전제로 한다. 결과를 보기 전에 두 앱 각각의 예측과 대안을 적고, 나중에 비교한다. 아래 왕복 수 비유에는 앞 절의 가산 모형 가정이 필요하다.

| 가설 | 오프라인 탐침 | 기울기 k | PCAP 직렬 깊이·연결 | 탭 이전 트래픽 |
|---|---|---|---|---|
| 캐시 후 갱신 | 이전 값이 보일 수 있음 | ≈ 0 가능 | 표시 뒤 갱신할 수 있음 | 있을 수도 없을 수도 있음 |
| 미리 받기 | 미리 받은 값이 보일 수 있음 | ≈ 0 가능 | 탭 후 요청 적을 수 있음 | 검색 결과 표시 때 있을 수 있음 |
| 탭마다 새 연결 | 로컬 표시·UI 정책에 따라 다름 | 연결 유형·재개·화면 의존성에 따라 다름 | 새 핸드셰이크 후보 동반 | 배경 트래픽이 있을 수 있음 |
| API 순차 호출 | 로컬 표시·UI 정책에 따라 다름 | 완료의 직렬 경로면 2 이상 가능 | 여러 송수신 묶음 후보 | 있을 수도 없을 수도 있음 |
| 실시간 스트림의 첫 상태 | UI 정책에 따라 다름 | 연결·구독과 지연 방향에 따라 다름 | 서버 발신 반복 패턴 후보 | 연결이 이미 열려 있을 수 있음 |
| 렌더링 등 다른 작업이 완료를 결정 | 해당 없음 | ≈ 0 가능 | 데이터가 먼저 도착할 수 있음 | 해당 없음 |

오프라인 성공은 캐시와 미리 받기를 구분하지 못한다. 실패도 연결 검사나 표시 정책 때문일 수 있다. k≈0은 이 조작에 민감하지 않았다는 뜻이며, 네트워크 사용이나 서버 병목의 부재를 뜻하지 않는다.

## 4. 장비와 보정

### 4.1 구성

```
인터넷 ─ (이더넷 또는 USB 테더링) ─ Mac ─ 인터넷 공유 Wi-Fi(bridge100) ─ Galaxy S24+
                                         └─ USB 케이블: adb ping, 영상 복사
```

- Mac의 Wi-Fi는 공유에 쓰이므로 인터넷은 Wi-Fi가 아닌 경로로 받아야 한다.
- 휴대폰은 Mac의 공유 Wi-Fi에만 연결한다. 모바일 데이터와 VPN은 끈다. 화면 측정 세션에서는 PCAPdroid도 끈다.
- 측정 중 다른 앱의 백그라운드 동기화를 줄이기 위해 대상 두 앱 외의 앱을 닫는다.

### 4.2 지연 주입 방식

`tools/hotspot_delay.py`는 macOS dummynet 파이프 17101을 만들고, Apple의 `com.apple/*` 앵커 지점 아래 `com.apple/stocklab-delay` 앵커에 규칙 한 줄을 넣는다.

```
dummynet in quick on bridge100 all pipe 17101
```

- 기본값(`--direction in`)은 휴대폰에서 나가는 패킷에 지연 전체를 건다. 왕복 시간은 방향과 무관하게 같은 만큼 늘어난다. `--direction both`는 지연을 업링크와 다운링크에 반씩 나눈다.
- 0ms 단계도 지연 0ms 파이프를 지나게 해서 모든 단계가 같은 경로를 쓴다.
- DNS를 포함한 휴대폰의 모든 트래픽이 지연된다. 두 앱에 같은 조건이다.
- pf는 참조 토큰(`pfctl -E`)으로 켜고, `off`가 그 토큰만 반납한다. 인터넷 공유가 pf를 쓰고 있으면 pf는 계속 켜져 있다.
- 관리자 권한이 필요한 명령은 `sudo`로 실행되며 Mac 비밀번호를 묻는다. 실행 전에 `--dry-run`으로 명령을 확인할 수 있다.

### 4.3 보정 (세션 전 필수)

`ping`은 USB로 연결한 휴대폰에서 `adb shell ping`을 실행한다. 대상 호스트는 앱 서버가 아니라 지연이 걸렸는지 확인하는 기준점이다.

```bash
python3 tools/hotspot_delay.py on --delay-ms 0 --ping 1.1.1.1
python3 tools/hotspot_delay.py on --delay-ms 100 --ping 1.1.1.1
python3 tools/hotspot_delay.py on --delay-ms 300 --ping 1.1.1.1
python3 tools/hotspot_delay.py status
python3 tools/hotspot_delay.py off
```

| 결과 | 판정 |
|---|---|
| +100 단계 ping 중앙값이 0 단계보다 90~110ms, +300 단계가 270~330ms 크다 | 통과 |
| 늘지 않는다 | 실패. `ifconfig -l`로 공유 인터페이스 이름, `sudo pfctl -s info`로 pf 상태, 휴대폰 Wi-Fi 연결을 확인 |
| 약 두 배로 는다 | 실패. 같은 패킷이 두 번 지연되는 것이다. `status`에서 규칙이 한 줄인지 확인 |
| 0 단계 ping의 최소·최대 차이가 30ms를 넘는다 | 핫스팟이 불안정하다. 위치·채널을 바꾸고 다시 잰다 |

원인을 찾기 전에는 세션을 시작하지 않는다. 설정값을 임의로 절반으로 바꿔 맞추지 않는다. dummynet 지연은 커널 시계 단위로 올림될 수 있으므로 실제 증가량은 ping 값으로 기록한다.

## 5. 세션 설계

### 5.1 고정 조건

시나리오, 종목, 검색 결과 행, 키보드 상태, 완료 기준, 웜 상태 준비, 화면 녹화·PTS 판독 규칙은 [본 실험 계획](EXPERIMENT_PLAN.md)과 같다. 장중 세션만 첫 분석에 쓴다. 지연 단계를 뺀 모든 조건이 같아야 `tools/fit_rtt_slope.py`가 분석을 진행한다.

### 5.2 단계와 반복 수

- 지연 단계: 0, 100, 200, 300ms.
- 4라운드 × 4단계 = **16블록 × 4회 = 64회 시도, 32페어, 단계당 8페어.**
- 라운드마다 네 단계가 한 번씩, 세션 ID로 정해지는 무작위 순서로 나온다. 시간에 따라 서버 부하나 기기 온도가 바뀌어도 특정 단계에 몰리지 않는다.
- 블록 안의 앱 순서는 `토스-한투-한투-토스`와 그 역순을 단계마다 반씩 쓴다.
- 대략적인 정밀도: 잔차 표준편차가 100ms라면 k의 95% 구간은 ±0.3 안팎이다. k=1과 k=3을 구분하기에 충분하다. 시도끼리 독립이라는 가정 아래의 어림이다.

### 5.3 대장과 DB

```bash
python3 tools/make_rtt_ledger.py --session-id 20261030-rtt-search > rtt-ledger-20261030-rtt-search.csv
python3 -m stocklab.server --port 8768 --db data/rtt-20261030-rtt-search.sqlite3
```

- 대장에는 `round, block, position, run_id, app, added_rtt_ms, network_type`이 미리 채워진다. 측정하면서 `ping_rtt_ms`, `actual_local_time`, `outcome`, 영상 정보를 채운다. `rtt-ledger*.csv`는 Git에서 제외된다.
- 대시보드에 입력할 때 `run_id`, `run_order`(= `position`), `network_type`은 **대장 값을 그대로** 쓴다. `network_type`이 `mac-hotspot+100ms`처럼 단계마다 달라서, 대시보드의 기존 페어 분석도 단계별로 따로 묶인다.
- 본 실험·예비 측정 DB와 섞지 않는다.

### 5.4 블록 하나의 순서

1. 대장에서 다음 블록의 `added_rtt_ms`를 확인하고 지연을 바꾼다.

   ```bash
   python3 tools/hotspot_delay.py on --delay-ms 200 --ping 1.1.1.1
   ```

2. 출력된 ping 중앙값을 그 블록 `position 1` 행의 `ping_rtt_ms`에 적는다.
3. 10초 기다린 뒤 본 실험과 같은 준비 동작으로 두 앱을 검색 결과 화면까지 맞춘다.
4. 대장 순서대로 4회 측정한다. 각 시도는 화면이 안정된 뒤 3초 기다리고 탭한다.
5. 10초 안에 완료되지 않으면 `timeout`으로 기록한다. 실패도 행을 지우지 않는다.

세션이 끝나면 반드시 지연을 해제한다.

```bash
python3 tools/hotspot_delay.py off
```

중단 규칙은 본 실험과 같다. 결과를 본 뒤 시도를 더하거나 단계를 바꾸지 않는다. 앱이 업데이트되거나 망 구성이 바뀌면 새 세션으로 시작한다.

## 6. PCAP 교차 검증 (같은 날 별도 세션)

기울기는 화면의 지연 민감도를, PCAP의 직렬 왕복 깊이는 시각 규칙으로 만든 사슬 후보를 보여 준다. 두 관측의 일관성은 보조 근거지만, 숫자의 일치만으로 요청 의존성을 확인하거나 독립적인 인과 검증이라고 부르지 않는다.

1. 지연 0ms 상태로 [NETWORK_METADATA](NETWORK_METADATA.md)의 절차(PCAPdroid, 탭 신호기, 앱별 10회)를 따른다.
2. 가능하면 +200ms에서도 한 라운드를 더 캡처한다. 새 연결 비율·사슬 후보·데이터 시각 패턴이 어떻게 변하는지 기록한다. 가산 모형의 예측과 비교하되, 암호화 데이터의 기능과 UI 의존성을 모르면 사슬을 확정하지 않는다.
3. 보고서에서 다음 값을 옮긴다.
   - `직렬 왕복 깊이 중앙값`과 `직렬 왕복 사슬`의 단계(DNS → TCP 연결 → TLS 핸드셰이크 → 요청 등)
   - `TCP 연결 중앙값(ms)`: 관측 지점에서 SYN부터 SYN/ACK까지의 값. 선택적으로 `--base-rtt`에 참고값으로 넣을 수 있다. 적합이나 성분 분해에는 쓰지 않는다.

**직렬 왕복 깊이의 정의.** 한 동작 안에서 각 요청이 앞 응답이 도착하는 동안이나 끝난 직후(`--chain-slack`, 기본 0.15초 안)에 시작된 왕복을 이어 붙인 가장 긴 사슬의 길이다. TCP 연결, TLS·QUIC 핸드셰이크, DNS, 요청-응답을 각각 1회로 센다. 시각만으로 판단하므로 앞 응답이 실제로 다음 요청의 조건이었는지는 모른다. 80바이트 이하의 작은 요청이 응답 직후 0.1초 안에 나가면 반응 패킷으로 분류되어 깊이가 낮게 잡힐 수 있다.

## 7. 분석

```bash
python3 tools/fit_rtt_slope.py --db data/rtt-20261030-rtt-search.sqlite3 \
    --ledger rtt-ledger-20261030-rtt-search.csv \
    --base-rtt toss=24 --base-rtt kis=19 \
    --out captures/rtt/report-20261030.md --json captures/rtt/report-20261030.json
```

- 대장의 모든 행에 `outcome`이 있어야 실행된다.
- 대장과 관측 status가 모두 `completed`인 시도만 적합한다. 시간 초과·오류는 단계별 건수로 따로 보인다.
- 기울기는 최소제곱 직선이다. 95% 구간은 **블록 단위 부트스트랩**이다. 같은 블록의 시도는 시간·서버 상태를 공유하므로 블록을 통째로 다시 뽑는다. 블록이 5개 미만이면 구간을 내지 않는다.
- `토스−한국투자(페어)` 열은 페어마다 차이를 구해 같은 방식으로 적합한다. 그 기울기가 "RTT가 1ms 늘 때 두 앱의 격차가 몇 ms 벌어지는가"다.
- 어느 단계든 완료 페어가 5쌍 미만이면 보고서 맨 위에 **예비 결과**로 표시된다.

## 8. 결과 읽기

| 관찰 | 해석 | 다음 확인 |
|---|---|---|
| k ≈ PCAP 직렬 깊이 | 가산 경로 후보와 양립하나 의존성은 미확인 | 새 연결 조건/없는 조건의 예측을 별도 세션에서 비교 |
| k < 깊이 | 중첩·배경 동작·사슬 추정 오차 등 여러 설명 가능 | `--chain-slack` 감도와 화면 시각 검토 |
| k > 깊이 | 사슬 누락·전송 적응·재시도 등 여러 설명 가능 | 수신 바이트·실패·비선형성과 분석 기준 검토 |
| k ≈ 0 | 이 지연 조작에 화면 완료가 민감하지 않음 | 캐시·미리 받기·렌더링·지연 방향을 함께 검토 |
| 단계별 중앙값이 직선을 벗어난다 | 시간 초과·재시도·경로 전환 같은 적응 동작 | 단계별 시간 초과, 높은 단계의 영상 재판독 |
| 페어 차이 기울기 구간이 0을 포함하지 않는다 | 이 구성에서 RTT가 늘수록 격차가 벌어진다(또는 줄어든다) | 같은 결과가 셀룰러 실측에서도 나오는지 |

**성분 분해를 하지 않는다.** 별도 캡처의 기본 RTT와 k를 곱해 실제 네트워크 시간으로 간주할 수 없다. 동일 경로·endpoint·작업 의존성과 0 RTT까지의 선형성이 확인되지 않았기 때문이다. 분석기는 `--base-rtt`를 참고값으로만 보관하며, 기존 `network_share_ms`·`non_network_ms` 및 해당 구간은 출력하지 않는다. 예비 측정의 650ms 차이도 이 계산으로 설명하지 않는다.

## 9. 결론 문장의 틀

아래 숫자는 **예시**다.

> 이 기기·이 망 구성에서 추가 지연에 대한 화면 완료 시간의 기울기는 토스 k=2.9(95% 구간 2.7~3.0), 한국투자 1.2(1.1~1.4)였다. 보정이 통과한 이 범위에서 두 화면의 RTT 민감도가 달랐다. 별도 캡처에서는 한 앱에 탭 근처의 새 연결이 더 자주 관측되어 연결 준비 비용을 후속 후보로 두었다. 캐시·렌더링·구독 준비도 아직 배제하지 못했다. 다음 세션에서 첫 진입과 재진입을 나눠 새 연결이 관측된 조건에서만 민감도가 커지는지 확인한다.

- 쓸 수 있는 말: "관찰된 행동이 X 구조의 예측과 일치하고 Y의 예측과 어긋난다", "이 구성에서 RTT 1ms당 격차가 k ms 벌어진다".
- 쓰지 않는 말: "토스의 아키텍처는 X다", "서버가 느리다", "HTTP/2·HTTP/3 때문이다". 회사 내부 로그 없이는 확정할 수 없다.
- 가장 강한 근거는 **미리 한 예측이 맞는 것**이다. 마지막 문장 같은 예측은 셀룰러 같은 다른 망의 실측으로 확인한 뒤에만 결과로 쓴다.

## 10. 사전 점검: 오프라인 탐침 (선택, 10분)

지연 실험 전에 캐시 가설을 빠르게 가른다. 두 앱을 검색 결과 화면까지 준비하고, 비행기 모드를 켠 뒤 종목을 탭한다. 이전에 연 종목과 처음 여는 종목을 각각 해 본다.

- 가격이 이전 값으로라도 보이면 사용할 수 있는 데이터가 이미 기기에 있었다는 가설과 일치한다. 로컬 캐시와 사전 수신은 구분되지 않는다.
- 로딩 표시나 오류만 보여도 탭 뒤 취득만이 원인은 아니다. 연결 검사·표시 정책이 있을 수 있다.

계좌·잔고 화면은 지나지 않는다. 결과는 영상과 메모로만 남기고 속도 통계에 넣지 않는다.

## 11. 한계

- **경로 차이:** 핫스팟 경로는 평소 Wi-Fi와 다르다. 이 세션의 절대 시간은 본 실험 결과와 섞지 않고 기울기만 비교한다.
- **업링크 지연:** 기본 설정은 휴대폰에서 나가는 쪽에만 지연을 건다. 요청이 필요한 대기는 모두 늘어나지만, 요청 없이 서버가 밀어주는 주기적 갱신의 도착 간격은 바뀌지 않는다.
- **지표 범위:** 최초 표시와 지속 갱신은 별도 지표다. 특히 업링크만 늦추는 실험으로 다운링크 푸시의 지연 민감도를 평가하지 않는다. 보정 누락·불일치 시 도구가 적합값을 출력해도 확정 분석에 사용하지 않는다. 대장과 관측의 `network_type` 불일치도 수정한 뒤 분석한다.
- **적응 동작:** 지연이 크면 앱이 시간 초과, 재시도, 다른 경로, 품질 저하로 동작을 바꿀 수 있다. 그 경우 직선 모형이 맞지 않으며 단계별 표로 드러난다.
- **측정 오차:** 판독 오차가 지연 단계와 독립적이면 주로 잔차를 키운다. 단계별 표시 방식이 바뀌거나 판독자가 조건을 알고 경계를 다르게 고르면 기울기도 치우칠 수 있다.
- **시간 변화:** 서버 부하·시세 활동은 시간에 따라 바뀐다. 라운드별 무작위 순서로 완화하지만 없애지는 못한다.
- **추론의 범위:** k는 설정 지연에 대한 민감도이며 왕복 횟수를 식별하지 않는다. PCAP 사슬도 시각 기반 후보다. 두 관측이 맞아도 내부 구조가 확정되지는 않는다.
- **스크립트 검증:** 지연 주입은 실제 핫스팟에서 아직 확인하지 않았다. 매 블록의 ping 기록이 그 검증 기록이다.

## 12. 저장과 공개

대장, 세션 DB, 캡처, 보고서 JSON은 Git에서 제외되는 위치에 둔다. JSON의 제외 목록에는 `run_id`가 들어 있으므로 그대로 공개하지 않는다. 공개 포트폴리오에는 단계별 중앙값, k와 구간, 직렬 깊이 요약, 해석 범위 문장만 싣는다.

이 결과로 [케이스 스터디의 경쟁 구조](CASE_STUDY_ROADMAP.md)를 갱신하고, 다음 세션에서 구분할 예측을 정한다. 모의 시세 서버는 특정 후보의 동작을 이해하기 위한 선택적 보조 실험이다. 자체 구현의 결과를 회사 내부 구조의 증거로 쓰지 않는다.
