# 비복호화 네트워크 메타데이터 비교

> 상태: 2026-10-15 기준 **도구 구현 완료, 두 앱의 실제 캡처 0건.** 분석기는 합성 패킷 테스트와 Mac에서 직접 보낸 HTTPS 요청 캡처(TLS 1.3, TLS 1.2, HTTP/1.1 강제)로 검증했다. 실제 PCAPdroid 캡처와 실제 QUIC 트래픽으로는 아직 검증하지 않았다.

화면 녹화 실험은 **사용자가 본 시간**을 잰다. 이 문서의 실험은 같은 탭 동작에서 **앱이 네트워크로 무엇을 했는지**를 본다. 두 결과를 합치면 "화면 완료 시간 중 네트워크가 차지할 수 있는 몫"과 "나머지 클라이언트 몫"을 나눠 볼 수 있다. 원래 질문인 "토스가 어떤 프로토콜·연결 방식 때문에 유리한가"에 답할 수 있는 근거는 이 단계에서 나온다.

## 1. 알 수 있는 것과 없는 것

| 관찰 항목 | 근거 | 이 자료로 말할 수 없는 것 |
|---|---|---|
| TCP+TLS인지 UDP+QUIC인지, QUIC 버전 | 패킷 헤더, QUIC long header | QUIC 안의 HTTP/3 여부 |
| 서버 이름(SNI), TLS 버전, ALPN **제안 목록** | ClientHello·ServerHello 평문 | TLS 1.3에서 서버가 고른 ALPN(암호화됨) |
| TLS 1.2의 ALPN **선택값**(예: h2) | TLS 1.2 ServerHello 평문 | 해당 연결의 모든 요청이 같은 API라는 사실 |
| 세션 재개(PSK·세션 ID), HelloRetryRequest, 0-RTT 제안 | 핸드셰이크 평문 확장 | 서버 측 캐시 적중 |
| 탭 1회당 신규 연결 수, 재사용 연결 수, DNS 질의 수 | 연결 시작 시각과 탭 시각의 대응 | 각 연결이 어떤 화면 요소를 담당하는지 |
| 연결 준비 시간(SYN → 첫 암호화 레코드) | 패킷 시각 | 실제 서버 RTT의 정확한 값(VPN 방식 오차) |
| 탭 후 첫 응답 데이터, 마지막 응답 데이터까지 | 요청이 선행된 서버 데이터 묶음 | 서버 처리시간, 시세의 최신성 |
| 요청 없이 서버 데이터가 반복되는 장시간 연결과 그 **간격 중앙값** | 타이밍 기반 추정 | WebSocket·SSE·gRPC 스트림 중 무엇인지, 화면 갱신 주기와 같은지 |

복호화, 인증서 설치, 인증서 고정 우회는 하지 않는다. 금융 앱의 약관과 보안 정책을 건드리지 않으면서도 위 표의 왼쪽 열은 충분히 비교할 수 있다.

## 2. 캡처 도구 선택

**기본: Android의 PCAPdroid.** 루트 없이 Android `VpnService`로 기기 안에서 트래픽을 받으며, 실제 외부 VPN 서버를 쓰지 않는다. 시작 전에 **앱 필터**로 대상 앱 하나만 지정할 수 있다. [PCAPdroid 빠른 시작](https://emanuele-f.github.io/PCAPdroid/quick_start)

- 덤프 방식은 **PCAP File**을 쓴다. 시작 버튼을 누른 뒤 저장 이름과 위치를 고른다. [덤프 방식](https://emanuele-f.github.io/PCAPdroid/dump_modes)
- PCAPNG 형식은 유료 기능이므로 필요 없다. 분석기는 일반 PCAP과 PCAPNG를 모두 읽는다.
- 설정의 **PCAPdroid extensions**(이전 이름 PCAPdroid trailer)를 켜면 패킷마다 앱 이름이 붙는다. 분석기가 이 값을 읽어 보고서의 "트레일러 앱 이름"에 표시한다. [고급 기능](https://emanuele-f.github.io/PCAPdroid/advanced_features)
- **TLS 복호화 기능은 켜지 않는다.** 복호화를 위한 QUIC 차단 같은 트래픽 변경 옵션도 꺼져 있는지 확인한다. QUIC을 차단하면 앱이 TCP로 바꿔 동작해 관찰 대상 자체가 달라진다.
- 앱이 VPN 사용을 감지해 경고하거나 동작을 막으면 **우회하지 않고 중단**한다. 그 사실을 "캡처 불가"로 기록한다.

VPN 방식 캡처의 시각은 앱과 PCAPdroid 가상 인터페이스 사이에서 찍힌다. 경로가 하나 추가되므로 이 세션의 시간은 화면 녹화 세션과 섞지 않고, **같은 캡처 방식의 두 앱끼리 상대 비교**로만 쓴다.

**대안: Mac 핫스팟 + tcpdump.** Mac이 유선 인터넷을 받고 **인터넷 공유**로 Wi-Fi를 내보내면, 휴대폰에 VPN을 켜지 않고 Mac에서 캡처할 수 있다. 대신 휴대폰의 모든 앱 트래픽이 섞이므로 서버 이름으로 앱을 구분해야 한다. 이 프로젝트의 Mac은 이미 `tcpdump` 사용 권한이 있다.

## 3. 세션 절차

화면 녹화 본 실험과 **다른 시간대의 별도 세션**으로 진행한다. 같은 Wi-Fi, 같은 종목·검색어·결과 행, 웜 상태, 동일한 준비 동작은 화면 실험과 똑같이 맞춘다. 장중과 장외는 별도 세션이다. 실시간 시세 스트림은 장중에만 활발할 수 있으므로 **장중 세션이 우선**이다.

1. 휴대폰과 Mac 모두 **자동 날짜·시간**이 켜져 있는지 확인한다. 탭 시각과 패킷 시각을 맞추는 기준이다.
2. 대상 앱을 종목 검색 결과 화면까지 준비한다. 계좌·잔고 화면은 지나지 않는다.
3. PCAPdroid의 앱 필터를 대상 앱 하나로 지정하고 **Start**를 누른다. 파일 이름은 `toss-01.pcap`처럼 앱과 순번을 붙인다.
4. Mac에서 탭 신호기를 실행한다. 15초마다 터미널에 `TAP NOW`가 뜨고, 그 시각이 `.marks` 파일에 저장된다.

   ```bash
   cd ~/MK/self-project/compare-stock
   python3 tools/tap_metronome.py --out captures/net/toss-01.marks --count 10 --interval 15
   ```

5. 신호가 뜰 때마다 같은 종목을 탭한다. 상세 화면에 이름과 가격이 보이면 약 6초 뒤 뒤로 가서 다음 신호를 기다린다. 10회가 끝나면 PCAPdroid에서 **Stop**하고 저장한다.
6. 앱 순서는 토스 → 한국투자 → 한국투자 → 토스로 교차한다. 한 라운드에 파일 4개가 나온다. 첫 라운드로 절차를 확인한 뒤 같은 조건으로 2~3라운드를 더 한다.

뒤로 가기, 광고, 로그 전송처럼 탭이 아닌 활동도 패킷으로 남는다. `.marks`와 시작 시각이 맞지 않는 동작은 보고서에서 **배경**으로 표시하고 요약 통계에서 뺀다.

## 4. Mac으로 옮기고 분석

PCAPdroid가 저장한 위치를 확인한 뒤 USB 디버깅으로 복사한다. Android SDK Platform Tools를 저장소의 `platform-tools/`에 풀었다고 가정한다. 이 폴더는 Git에서 제외된다. `cd` 경로는 저장소를 받은 위치에 맞게 바꾼다. 아래는 다운로드 폴더에 저장한 경우다.

```bash
cd ~/MK/self-project/compare-stock
./platform-tools/adb shell ls -l /sdcard/Download
./platform-tools/adb pull /sdcard/Download/toss-01.pcap captures/net/
./platform-tools/adb pull /sdcard/Download/kis-01.pcap captures/net/
```

두 앱의 캡처를 한 보고서로 비교한다. 각 인자는 `라벨=파일` 형식이다.

```bash
python3 tools/analyze_pcap.py toss=captures/net/toss-01.pcap kis=captures/net/kis-01.pcap --marks toss=captures/net/toss-01.marks --marks kis=captures/net/kis-01.marks --out captures/net/report-01.md --json captures/net/report-01.json
```

탭 표시 일치 건수가 10/10에 못 미치면 경고가 나온다. 시계 동기화를 확인하고, 앱이 탭 직후 요청을 늦게 보내는 경우에만 `--idle-gap`을 조정한다. 조정값은 보고서 맨 아래 "설정" 표에 남는다.

## 5. 보고서 읽는 법

| 보고서에서 본 것 | 다음에 세울 가설 | 확인 방법 |
|---|---|---|
| 한 앱만 탭마다 신규 TLS 연결이 생긴다 | 연결 재사용 부족이 체감 지연에 더해진다 | 그 앱의 `TLS 연결 준비 중앙값`이 화면 시간 차이를 설명할 크기인지 비교 |
| 한 앱만 QUIC을 쓴다 | 1-RTT 연결 설정과 손실 회복 방식의 차이 | 신규 연결 비율이 낮으면 영향도 작다. HTTP/3라고 쓰지 않는다 |
| 서버 주도 반복 전송 연결이 장중에만 보인다 | 실시간 시세를 밀어주는 스트림 | 장외 세션과 비교. 화면 진입 시 첫 응답이 이 연결에서 오는지 확인 |
| 두 앱의 서버 주도 전송 간격이 크게 다르다 | 시세가 "빨리 바뀌어 보이는" 체감 차이 | 같은 장중 시간대·종목에서 간격 중앙값 비교. 화면 숫자 변경 주기를 영상으로 따로 확인 |
| 네트워크 구간은 비슷한데 화면 완료 시간 차이가 크다 | 클라이언트 처리·렌더링이 차이를 만든다 | Perfetto 시스템 추적으로 프레임 단계 확인 |
| 네트워크 구간 차이가 화면 차이와 비슷하다 | 서버 응답·데이터 크기·호출 횟수 차이 | 동작당 수신 바이트와 호출 서버 수 비교 |
| 첫 응답이 빠르고 마지막 응답이 늦다 | 화면을 나눠 그리는 단계적 로딩 | 화면 녹화의 첫 반응·완료 시점과 대응 |

**분해 계산의 예.** 화면 실험에서 한 앱의 완료 시간 중앙값이 700ms이고, 이 세션의 네트워크 구간 중앙값이 150ms라면, 네트워크 외 시간은 최대 약 550ms로 볼 수 있다. 두 값은 서로 다른 세션의 중앙값이고 VPN 경로 차이도 있으므로 **대략적인 비중**으로만 쓴다. 이 비중이 크게 다르면 다음 실험의 방향이 정해진다.

`protocol_observation` 후보 문장이 각 앱 상세 아래에 나온다. 대시보드에 옮길 때는 "별도 네트워크 세션 관찰"이라고 메모한다. 같은 시도에서 측정한 값처럼 쓰지 않는다.

## 6. 한계

- **VPN 경로:** 연결 준비 시간의 절대값은 실제 망 RTT와 다를 수 있다.
- **연결 공유:** HTTP/2·QUIC은 한 연결에 API와 스트림을 함께 실을 수 있다. 이때 탭 요청과 실시간 데이터가 한 연결에서 섞여 패턴 판정이 흐려진다.
- **이름 가림:** Encrypted Client Hello를 쓰면 SNI가 실제 서버 이름이 아닐 수 있다. 보고서는 ECH 사용 연결 수를 따로 센다. 암호화 DNS를 쓰면 DNS 이름 매핑이 비어 서버가 IP로 표시된다.
- **판정 기준값:** 데이터 묶음 간격 0.25초, 반응 패킷 0.1초·80바이트 같은 기준은 경험적 값이다. 결과가 기준값에 민감한지 보려면 `--idle-gap`을 바꿔 다시 실행해 비교한다.
- **표본:** 한 라운드 10회로는 경향만 본다. 화면 실험처럼 미리 정한 횟수를 지키고, 결과를 본 뒤 탭을 더하지 않는다.

## 7. 저장과 공개

`captures/`와 `*.pcap`, `*.pcapng` 파일은 Git에서 제외했다. 원본 캡처에는 기기 IP와 다른 도메인이 들어 있을 수 있으므로 공개하지 않는다. 보고서와 JSON에는 기기 주소, 패킷 내용, HTTP 경로를 쓰지 않는다. 그래도 공개 전에 서버 이름과 시각을 직접 검토한다. 공개 포트폴리오에는 앱별 집계 표와 해석, 검증 방법만 싣는다.
